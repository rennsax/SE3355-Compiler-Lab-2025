# LLVM版本升级报告
- 由于LLVM版本的lab引入了很多额外的特性，记录在这个文档里面
## 函数形参表和栈帧设计
- 目前版本的llvm函数形参表形如：func(%caller_sp, %sl, ... )

  即第一个llvm参数为调用者的sp值，第二个llvm参数为其静态链的父节点（同原始lab），后续的llvm参数为tiger源码显式定义的参数。

- %sp_caller会通过一个减法操作，计算得到当前context的新%sp，标记为%sp，所有的%sp在后续的codegen中需要被映射到实际的%rsp

- 由于LLVM要求SSA，使用寄存器来表示SimpleVar有困难，需要引入大量DAG分析。所以目前版本下所有的SimpleVar和形参都直接分配在栈上，其中的caller_sp不会出现在codegen，所以跳过不分配在栈上，sl默认是栈上方offset=8的位置（同样是扣掉了ret地址的位置。

  （后面codegen的栈如何与现在的栈对齐，还有一些挑战需要解决）

## AST节点的返回值，以及左值右值问题
- 每次translate调用都会返回一个llvm Value，llvm Value的type可能有两种可能。一种是与字面类型相同，也就是作为右值时的类型。另一种是字面类型的指针类型，也就是作为左值时的类型。这个设计的原因当下层节点是SimpleVar或者FieldVar或者SubscriptVar时，他们可能是左值也可能是右值，因此都默认作为左值处理，在上层发现是右值时再进行额外的load。而如果下层节点int或者RecordExp或者StringExp这类常量，那么他们不会存在左值形式，只能直接传递右值。

  而由于不确定下层节点返回的是左值还是右值，上层节点需要对下层的返回值进行类型检查（具体来说是检查返回值类型和理论类型之间的关系）

## 手动管理栈对象的设计思路
- 目前复用了tiger的frame数据结构进行栈帧的管理，通过在frame上分配OnFrameAccess来自动维护offset，然后每次具体需要使用某个栈上对象的时候，就通过offset和static link数据，生成一系列的计算地址的代码，最后把算出来的地址强转为目标类型的指针，就得到了对应对象的左值。
